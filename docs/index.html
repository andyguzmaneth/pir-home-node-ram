How much RAM does a 32 GB home node leave for a PIR server?

Squeeze test on a Reth + Lighthouse mainnet node, 2026-10-24 to 2026-10-26. Andy Guzman, CROPS Reads (Ethereum Foundation). Data span: .

TL;DR

  • The clients and the kernel need about GB (Reth heap , Lighthouse , kernel and other ). With no PIR server, the rest of the RAM fills with page cache ( GB, mostly Reth's database) and kernel buffers. The node uses that cache, but it gives the cache up when a PIR server needs the RAM.
  • A PIR server can hold 18 GB and the node stays at head (high confidence: passed in two runs, 0.7–1.2 GB of RAM left). At 18.5 GB the machine ran out of memory: the kernel killed the PIR process 5 times in 35 minutes. Reth and Lighthouse were never killed, because the PIR process was set to be killed first.
  • PIR database size that fits: about 4.5 GB with a 4x RAM rule of thumb, or about 11.2 GB with InsPIRe GPU's 1.6x. For planning, we suggest a budget of 16 GB of RAM (4 GB DB at 4x, 10 GB at 1.6x). This leaves room for Reth's heap to grow and for the PIR server's own working memory.
  • RAM never made the node fall behind. As the PIR server took RAM, Reth read more from disk (0.8 to 3.6 MB/s). Block import stayed under 350 ms (95th percentile), and lag stayed at about 8 s (under 1 block).
  • When the node fell behind, the cause was Lighthouse, not RAM. Lighthouse sometimes stopped sending new blocks to Reth for up to 13 minutes. This also happened with no PIR memory held, and it ended run C at 15 GB.

1. Where the 32 GB goes

Each bar is one state of the machine. In the top bar the node runs with no PIR server. The bottom bar is the end of the 18 GB step in run B. The PIR memory came out of the page cache ( GB) and reclaimable kernel buffers ( GB). Reth and Lighthouse kept their memory.

Values are medians. "No PIR" uses samples (15 s apart) from a quiet period between runs B and C, when Reth was fully warm. "PIR 18 GB" uses the last 10 minutes of that step. GB in this report means GiB (230 bytes), as the kernel reports it. "Kernel, buffers, slab" is total minus free minus page cache minus process memory. Lighthouse is its resident set, which includes a small amount of file cache.

4. What the squeeze costs

The node stays at head, but the PIR memory moves Reth's database from RAM to disk. These costs grow with PIR RAM. This test ran on a fast NVMe SSD. On a slower disk, the same reads could make the node fall behind.

Each dot is one clean step from run A or B. A steps 6, 8 and 10 GB are left out: swap was on during those steps, so the node had extra room. Reth DB in RAM is the part of mdbx.dat resident in page cache (fincore, every 5 min).

5. Falling behind is a Lighthouse/network problem

  • During every episode more than 60 s behind, Reth imported blocks in 44–360 ms (95th percentile). Reth was not slow. It received no new blocks.
  • Reth logged "Beacon client online, but no consensus updates received". Lighthouse's execution hash stopped advancing, and it had only 4–20 peers.
  • All episodes were in the local evening or night: a cluster at 19:50–20:25 local with the home bandwidth cap (20/10 Mbit/s) on, and the run C stall at 22:30–01:05 local with the cap off. The longest lasted 13 minutes.
  • In run C a stall started at 15 GB and went on after all PIR memory was released: the node was 438 s behind with 0 GB held.
  • We did not isolate the root cause (Lighthouse peers, the home network, or the bandwidth cap).

After release, the node was back at head in 5 min (A, B) and 21 min (C, during the stall). After a reboot the node caught up at about 37 blocks/min, about 7 times real time (one hour of lag in about 9.5 min).

7. Caveats

  • Dummy PIR server. It holds RAM and does nothing else: no CPU, no memory bandwidth, no disk. A CPU PIR server reads its whole DB for each query, so it competes with Reth for CPU and memory bandwidth. That part is not measured. No CPU build of the PIR scheme we target exists yet, so a dummy stands in.
  • DB size from blowup factors. The 4x figure is a rule of thumb, and 1.6x is InsPIRe GPU's resident footprint. A different scheme needs its own memory profile.
  • --minimal Reth node. A full EIP-7870 node does not fit on the 1.2 TB disk (about 1.3 TB even pruned). The minimal node has the same state and heap, but a smaller DB on disk. A full node's page cache would want more RAM, so it would feel the squeeze sooner.
  • Fast disk. The disk is an NVMe SSD (990 PRO) behind Proxmox, with 0.11–0.15 ms read latency. We did not check whether the host caches the disk; the latency suggests it does not. At 18 GB Reth made about 700 disk reads per second, against about 150 with no PIR. On a SATA SSD or an HDD, that could make the node fall behind.
  • Lighthouse backfill. Lighthouse was downloading historical blocks for the whole test (checkpoint sync), which added some disk and network load.
  • Swap in run A. A DAppNode timer turned swap back on during A steps 6–10 GB, so those steps are excluded. After that, a guard kept swap off.
  • Baseline drift. Reth's heap grew from 2 GB to 5 GB in the first day after a restart. Run B (two days of uptime) has the cleanest numbers.
  • One machine, one weekend. One home network with a daytime bandwidth cap of 20/10 Mbit/s. Runs were at night with no cap (04:15–12:45 UTC).

8. How to reproduce

Machine

  • Proxmox VM: 32 GB RAM (ballooning off), 8 vCPU (Ryzen 9 9900X), 1.2 TB disk, Debian 12.
  • Reth v2.8.0 (Docker, reth node --minimal, from a reth download --minimal snapshot). Lighthouse v8.3.0 (native, checkpoint sync).

Harness

Python scripts (stdlib only) and systemd units, in harness/. The raw data is in data/.

UnitWhat it doesOutput
pir-collectEvery 15 s: RAM (available, page cache, Reth and Lighthouse resident memory, Reth DB pages resident), CPU, disk, network, page faults, pressure stall info, head lag, peerssamples.csv
pir-blocksOne row per block from the Reth journal: arrival delay (network/CL) and import time (Reth)blocks.csv, events.log
pir-holderDummy PIR server. Holds the target GB as anonymous memory, touched once, in 256 MiB chunks. oom_score_adj=1000, so the kernel kills it before the clientsheld_gb
pir-orchestratorRuns the plan: precheck at head, ramp 2 GB every 2 min, then steps, release, recovery timingresults.json, report.md

Steps

1. Sync the node to head. Stop every other service. Turn swap off: sudo swapoff -a
2. Copy the harness to ~/pir-ram and install the units:
     sudo cp units/*.service /etc/systemd/system/ && sudo systemctl daemon-reload
3. Edit plan.json (runs, step sizes, hold minutes, deadline), then:
     sudo systemctl enable --now pir-collect pir-blocks pir-holder pir-orchestrator
4. Wait. Each run writes results.json. After the last run the orchestrator turns swap
   back on, restarts the stopped services and writes report.md.

Rules. Pass: the median lag over the last 15 minutes of the step is 24 s or less. Fail: above 24 s, or more than 120 s behind for 5 minutes in a row. Network: a failed step where Reth's import p95 stayed under 4 s is marked "net" and repeated once. Ceiling: the run stops when free RAM minus the next increase falls below the margin (0.5 GB in A and B, 0.1 GB in C). OOM: a restart of the PIR process fails the step (added after the test, see the appendix). Recovery: after release, the time until lag stays at 24 s or less for 5 minutes.

To test a real PIR server: replace pir-holder with the server process, loaded with a DB sized for each step, and send it a steady query load. That measures the CPU and memory-bandwidth contention this test left out.

Appendix: every step

Outcome "net": the step failed on lag while Reth kept importing fast, so it was repeated once. Run C's repeat at 15 GB also failed, during the same Lighthouse stall that went on after release. Outcome "oom": the kernel killed the PIR process during the step (from the kernel log). The orchestrator logged B 18.5 GB as a pass, because systemd restarted the process and it refilled in about 20 s; the harness now fails a step on any restart.
